A look-ahead audit that shared the defect it was checking for

A look-ahead audit passed on every run because it derived its dates the same way as the calendar it audited. Every figure on that base was withdrawn and re-measured.

#LookAhead #Validation #Backtesting

The problem

A walk-forward simulation fits a model on past data, tests it on the following period, steps forward and repeats. Its characteristic failure is look-ahead: a decision using information not yet available. In September 2026 the walk-forward runs of an earlier internal configuration (a historical backtest, since superseded and not among the results reported on this site) carried an automated no-look-ahead audit, which passed on every period of every run. A second machine was reproducing the research harness (the simulator that runs these walk-forward tests), and the figures were headed into the record of a pending build.

Initial approach

The audit was treated as assurance. That was reasonable: it was written for exactly this purpose and had passed on every run of this configuration. A reproduction of the figures on another machine, to the dollar, was recorded as supporting evidence. The audit itself was untested.

What didn't work

On 19 September 2026 a reconciliation between the backtest and a second replay engine produced a fix to how the walk-forward calendar derived session dates. Recorded symptoms: non-trading days in the calendar, one weekday missing, test windows opening early, and a point-in-time filter admitting an input before it existed. The fix reached the engine code line but not the research harness copies.

On 21 September, on a second research machine set up from the newer code line I had chosen as its base, the old and the corrected base were run with the same data, configuration and settings. In this earlier internal historical backtest, gross profit was a little more than a third lower on the corrected base. The audit had passed on both.

Investigation

  1. A confounded gate. The first parity gate, a tolerance band, changed code base and data store together, so it could not attribute its own failure. It was withdrawn for the same-machine comparison.
  2. Two alternatives discarded. Shorter early history on one machine, and corporate actions, were each tested and dropped on arithmetic.
  3. The data store exonerated. The old code matched to the dollar across two machines on most periods, and a byte-for-byte re-run placed the whole remaining difference in the earliest periods, where one machine had shorter history.
  4. The fix, read in full. The gap was at first treated as code-base drift to be documented. A review that read the fix itself, not its subject line, found it also patched the audit, which computed its dates with the same conversion as the calendar.
  5. Scope and mechanism. The defect sat in seventeen harness copies at two places; the second generated the shifted calendar. The conversion was correct under only one time-zone setting, and the runs used a different one.

Iteration

I made four decisions on 21 September, three on this episode. The comparison runs already specified, run on the corrected base, would be the re-measurement. Development would continue on code only and quote no numbers, against a written list of every withdrawn figure. The pending build was held until those runs reported.

The active harness copies were patched behind a new build label and the old build was left untouched, so earlier results stay reproducible. A regression fixture was added, a test that fails if the bare date conversion returns. That evening the calendar was not redefined to get past a data gap; the missing history was backfilled instead.

Validation

  • Same machine, data and configuration; only the code base differed.
  • The old code agreed across two machines, to the dollar, on most periods, which cleared the data store, not the code.
  • An independent generator reproduced the wrong calendar under the real time-zone setting and the correct one under the other.
  • The regression fixture passed on the patched build.

The size is one pair of runs on one machine. The decision note declines to call the whole difference leaked profit: it combines removing a look-ahead with shifting every walk-forward boundary, and the two were not separately quantified. A deliberate leak-injection test of the audit has not been run, so the claim that the audit now works rests on that fixture. The post-mortem is complete; that test remains open.

Result

The result got worse. Correcting the calendar lowered that earlier internal backtest’s gross profit by a little more than a third, with the caveat above. Every absolute figure of that configuration was withdrawn, and it was re-measured on the corrected base later that week (see the replay-parity case). Rankings between variants were described as probably intact, and not verified until then. Every earlier pass from the audit was recorded as void, not merely suspect. The next morning a checksum showed the earlier cross-machine reproduction had run the same uncorrected file: consistency, not correctness.

Lesson

A green check is evidence only if its measurement path is independent of the code it audits. The test adopted for any gate: if the build were wrong in exactly the way this step checks, the step must fail. By that test the repaired audit is itself unproven until a planted leak makes it fail.

On 28 September a second look-ahead in the research harness was found only because a second engine keyed its decisions differently and the trade lists disagreed. The rule recorded then: test every mechanism that carries portfolio state against a second implementation on a common slice of history. On 2 October a point-in-time audit asked of each input whether it was knowable at the fitting date (see the point-in-time universe case).
