When the replay disagreed with the real-time record

A replay disagreed with the trading engine's real-time record while all of its checks passed. My explanation was wrong, and the audits I then asked for found defects in the replay.

#ParityTesting #RealTimeRecord #Backtesting

The problem

A replay re-runs history through trading code. One such replay disagreed with the trading engine’s real-time record over a common window. The size and direction of the gap are not given. No live or paper-trading results are shown here. The comparison below is in fills, entry prices and exit reasons. If the replay could not reproduce a period the engine had already traded, its output for any other period was in doubt.

Simulations here are historical backtests of an earlier internal configuration, not a tier reported on this site.

Initial approach

The replay drove the engine’s own trading classes under a frozen clock (the system time pinned to each historical moment), a better start than a parallel reimplementation. Its output passed a verifier of nearly 200 automated checks: the ledger added up, each statistic recomputed from it, and the report showed the same figures. It was assumed comparable with the real-time record.

What didn't work

Every check passed, yet I did not believe the replay and said so: over exactly that period it gave a different answer, so it must be calculating a key quantity wrongly. I also asked whether it was running stale logic.

My explanation was wrong in mechanism. The replay was not miscalculating the quantity. Some open positions were not evaluated at all: the replay’s own loop skipped one call that the engine’s loop makes.

Investigation

  • Comparing holding times with the real-time record’s, then auditing which open positions the replay evaluated, isolated that defect.
  • Defects had surfaced one at a time, each after hours of running, so I asked for adversarial searches against the replay in parallel with every simulation, stopping and relaunching on any finding. Four passes (orchestration, fills, data and time sources, arithmetic) and three relaunches followed.
  • At least nine defects were recorded, including order size mis-scaled by a stale default, replay state written into tables the trading engine reads, and fills booked when no order could have filled. Two were created by earlier fixes: in one, a second reference to the system clock was left unfrozen, so a guard that depended on it never acted.
  • Part of the disagreement was not a defect: the engine’s rules had changed during that period, while the replay, as I had specified, applied one configuration throughout. On the one like-for-like window, the replay’s value of that quantity matched the engine’s logged value (median difference zero).

Iteration

Fixes went into the replay’s driver, not the code it drives, and every override is recorded beside the output. Guards were proven by counters that must move: one rose from zero after the clock fix. Differences left unfixed were listed and stamped on the output.

I warned that the test suite held stale and contaminated material. Among the rules recorded: trace every number an inherited test or default reads to the run’s own configuration; verify a guard by breaking what it guards.

I then set the rule that engine updates would be decided on this replay, two versions side by side, once I gave the go-ahead. By 4 October that comparison had not been run; it remains open, outside this completed post-mortem.

Validation

The corrected replay, started from an empty book, was compared with the real-time record, the control, over the like-for-like window.

  • About two-thirds of the recorded fills were reproduced.
  • Entry prices were about 3 basis points apart.
  • The exit reason was identical on every paired completed trade.

This is a partial check on a short slice. Unpaired fills were attributed to model state upstream of sizing and not quantified. On earlier history, with every open position evaluated, the replay’s result at that revision was recorded as an open question.

Result

The replay became more trustworthy and its limits explicit; it is not a proof of equivalence.

The lesson then reached a different instrument, the research replay harness that produces the backtests reported on this site: a containerized walk-forward simulator (its calendar defect is another case). On 25 September a parity comparison exposed in it a second, undeclared risk limit that refused entries. Every figure measured under it was withdrawn and restated in a dated report listing which verdicts survive. The reference result rose; a variant then recommended over it kept a narrower advantage, and its drawdown became the deeper of the two.

On 28 September, running the engine’s code and the harness over a common slice found eight harness defects, including a second look-ahead, a rule counted in the wrong unit, and a position-sizing error. One was a half-applied fix (one call site changed, another not) that oversized positions in some configurations until the comparison caught it the same day. By that evening the variant’s advantage was gone.

At the first restatement, the harness and a separately built second implementation agreed within a fraction of a percent on shared fitted inputs and differed by 5 to 12 percent in simulated ending value when each fitted its own.

Lesson

A replay reproduces the engine only along the code path it calls. A self-consistent harness cannot find its own defects; a partner implementation on a common slice can. Passing checks describe the system as it was when their fixtures were written.

That 5 to 12 percent is the one measured guide I have to how far a single-implementation simulation can be off; this site’s headline figures are one implementation and say so.
